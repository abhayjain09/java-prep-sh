# Module 12 — Interview Questions

Organized by service group, then by level (beginner → intermediate → senior → scenario), matching [README.md](README.md)'s structure. Each includes an ideal answer outline and likely follow-ups.

AWS is asked everywhere on this repo's target company list, but weighted differently: expect it to be **central and deep** at Amazon (an AWS-native shop; expect drill-down past "what" into "why this service and not that one, at this scale, with this cost profile"), **heavily practiced** at Microsoft/Google/Oracle/Adobe/Salesforce (multi-cloud-aware interviewers who still expect fluency, often comparing against their own cloud's equivalents), and **compliance/security-flavored** at S&P Global/JPMorgan/Goldman Sachs (IAM least-privilege, audit trails via CloudTrail, encryption at rest/in transit, and Well-Architected's Security pillar get disproportionate attention in regulated-industry interviews versus, say, a scrappy startup that just wants "can you stand up a VPC").

## IAM

**Beginner:** "What's the difference between an IAM user, role, and policy?"
*Ideal answer:* A user is a long-lived identity (often a human, sometimes legacy machine access) with its own credentials. A role is an identity with **temporary** credentials, assumed by a person or an AWS resource (EC2, ECS task, Lambda) — no long-lived secret to leak. A policy is the JSON document, attached to either, that actually grants or denies specific actions on specific resources.
*Follow-up:* "Why would you attach a policy to a role instead of a user for an application?" → Because the application isn't a person — it's a resource (an ECS task, in this system) that should get exactly the permissions it needs via temporary, auto-rotating credentials, never a static access key that could leak in a log or a commit.

**Intermediate:** "Walk me through the IAM policy you'd write for this system's ECS task role."
*Ideal answer:* Reference the three-statement policy from README.md §1: `s3:GetObject`/`s3:PutObject` scoped to the exports bucket ARN, `sqs:SendMessage`/`sns:Publish` scoped to the fulfillment topic/queue ARN, `secretsmanager:GetSecretValue` scoped to exactly the DB-credentials and JWT-signing-key secret ARNs. Explicitly name what's **excluded**: no `iam:*`, no wildcard resources, no permissions for buckets/queues belonging to unrelated services.
*Follow-up:* "What's the difference between the ECS task role and the ECS execution role, and why do both exist?" → Execution role is used by the ECS **agent** to pull the container image and ship logs (infrastructure-level); task role is assumed by the **application code** itself (least-privilege, business-scoped). Conflating them either breaks deployment or over-grants the running app.

**Senior:** "Why should root account access keys never be used in an application, even 'temporarily' during a migration?"
*Ideal answer:* The root user's access is unconditional and unrestrictable by any policy — there's no way to scope it down. A scoped IAM role's leaked temporary token is bounded damage (exactly its granted permissions, until expiry); a leaked root key is unbounded, full-account damage (every resource, every dollar of spend, the ability to close the account or disable billing alerts). AWS's own hardening guidance ranks deleting root access keys as one of the first account setup steps, precisely because "temporary" root key usage is one of the most common real-world root-cause patterns in large breaches.
*Follow-up:* "How do you enforce this organizationally, not just by convention?" → Service Control Policies (SCPs) at the AWS Organizations level can deny root-user API actions account-wide; IAM Access Analyzer and scheduled credential reports can flag any root access key that still exists; MFA delete + hardware MFA on the root user itself as a break-glass control.

**Scenario:** "A security audit finds an ECS task role with `s3:*` on `Resource: "*"`, attached eight months ago 'to get the export feature working faster.' How do you remediate it without breaking production?"
*Ideal answer:* Don't revoke immediately — first use CloudTrail (or IAM Access Analyzer's policy-generation feature, which mines CloudTrail history) to see exactly which S3 actions and resources the role has actually used over a representative window. Draft a scoped replacement policy from that evidence, deploy it in parallel/monitor mode if the tooling supports it (or to a staging environment first), then cut over and monitor for `AccessDenied` errors before removing the broad policy. This is the practical, safe version of least-privilege remediation — evidence-driven, not guessed.

## VPC & Networking

**Beginner:** "Why does RDS sit in a private subnet with no public IP, when the ALB is public?"
*Ideal answer:* The ALB's entire job is accepting inbound internet traffic — that's the one component designed for it. RDS should never be reachable from the internet at all; a public IP on a database is one of the most common real-world breach root causes. Private subnets plus a security group allowing inbound only from the app tier (not the whole internet) is the correct posture.

**Intermediate:** "Explain the difference between a security group and a network ACL, and where each is used in this system's design."
*Ideal answer:* Security groups are stateful and resource-scoped (the ALB SG → app SG → RDS SG chain in [terraform/vpc.tf](terraform/vpc.tf), each an explicit allow-list referencing the *other security group*, not a CIDR block); a reply to an allowed inbound request is automatically permitted out, no separate outbound rule needed. NACLs are stateless and subnet-scoped, evaluated in numbered order, and support explicit deny — used sparingly as a coarse subnet-level backstop, not the primary control here.
*Follow-up:* "If a security group already denies everything by default, what does a NACL add?" → Defense in depth: a NACL-level explicit deny (e.g. blocking a known-bad CIDR range across an entire subnet) still applies even if a security group is later misconfigured to be too permissive — it's a second, independent layer that doesn't rely on the same rule set being right.

**Senior:** "Why use a NAT Gateway instead of just giving private-subnet resources a public IP with a security group locking down inbound?"
*Ideal answer:* A public IP is inherently addressable from the internet — even with a tight security group, that's one more layer that has to be configured correctly forever, and a future misconfiguration (or a mistakenly-attached, over-permissive security group during some later change) directly exposes the resource. A NAT Gateway makes the *architecture itself* enforce one-directional traffic — there's no public IP to misconfigure into being reachable, because there isn't one at all. This is the same "defense via architecture, not just configuration" principle behind RDS's isolated subnet having no route out at all.
*Follow-up:* "What's the cost trade-off of a NAT Gateway, and how would you reduce it for AWS-service-only traffic?" → NAT Gateway bills per-hour and per-GB processed; VPC Gateway/Interface Endpoints let traffic to specific AWS services (S3, Secrets Manager, etc.) skip the NAT Gateway (and its per-GB charge) entirely for that traffic, while third-party/internet-bound traffic still needs NAT.

**Scenario:** "Your team inherits a VPC where someone gave the RDS instance a public IP 'temporarily for local development' two years ago, and it's still there in production. Walk through your remediation plan."
*Ideal answer:* Immediate: confirm via the security group and any available access logs/CloudTrail data whether it's actually been exploited, not just exposed — don't assume "nothing happened" without checking. Then: schedule a maintenance window to disable `publicly_accessible`, verify the security group already restricts inbound properly (it should — public IP shouldn't have been the *only* control), test connectivity from the app tier through the private path first in staging, then cut over in production, and add automated detection (e.g. AWS Config rule flagging any public RDS instance) so this can't silently recur.

## Compute Choice (EC2 / ECS / EKS) & Serverless (Lambda/API Gateway)

**Beginner:** "What's the core difference between ECS and EKS?"
*Ideal answer:* Both are container orchestrators; ECS is AWS's own proprietary orchestration model (task definitions, services, clusters), while EKS is managed Kubernetes — the actual Kubernetes API, CRDs, and ecosystem tooling, with AWS managing the control plane but you still operating everything Kubernetes itself exposes.

**Intermediate:** "Why did you choose ECS Fargate over EKS for this Order/Inventory system, and what would change your mind?"
*Ideal answer:* Give the README.md §3 justification directly: this is one REST API plus a background consumer, not a multi-team, many-service system — Kubernetes' power (service mesh, complex traffic-shaping, CRD extensibility) solves problems this system doesn't have, at a real operational cost (a platform team to run it well). Fargate removes even ECS's own host-management layer, matching the system's actual complexity. Name the threshold explicitly: 15+ independently-deployed services, multi-team ownership, or genuine multi-cloud portability requirements would tip the calculus toward EKS.
*Follow-up:* "Isn't Kubernetes more portable if you ever need multi-cloud?" → Yes, and that's a legitimate reason to choose it — but only when multi-cloud portability is an actual, stated requirement, not a hypothetical "just in case." Optimizing for a requirement you don't have yet is exactly the over-engineering trap this question is probing for.

**Senior:** "When would Lambda + API Gateway be a *better* choice than ECS Fargate for a piece of this system, and what's the catch?"
*Ideal answer:* README.md §4's CSV/import example: an S3-upload-triggered Lambda for bursty, infrequent, latency-tolerant work costs nothing when idle and needs zero provisioned capacity. The catch is cold starts — Java Lambda cold starts are among the slower runtime profiles, a real risk for latency-sensitive, high-frequency synchronous calls, mitigated (not eliminated) by Provisioned Concurrency (fixed extra cost) or GraalVM native-image compilation (build complexity). The core REST API stays on Fargate because it's steady-traffic and connection-pooled in a way that doesn't suit per-invocation billing or cold-start risk.
*Follow-up:* "How would you decide, with data, whether a workload's steady-state traffic makes Fargate or Lambda cheaper?" → Model actual invocation count/duration against Lambda's per-ms-per-MB pricing, versus one or two small Fargate tasks' constant per-hour cost at the traffic's actual utilization — at genuinely steady, non-trivial request volume, an always-on Fargate task's amortized cost typically beats Lambda's per-invocation premium; at sparse or bursty volume, Lambda usually wins. Measure, don't assume either direction.

**Scenario:** "Amazon-style: your service currently runs on 10 EC2 instances behind an ALB, manually scaled by an on-call engineer during traffic spikes. Leadership wants less operational toil. Propose a path forward and defend it against 'why not just move straight to Kubernetes.'"
*Ideal answer:* Propose migrating to ECS Fargate with target-tracking auto-scaling (mirroring [terraform/ecs.tf](terraform/ecs.tf)'s `aws_appautoscaling_policy`) as the immediate fix for "manual scaling is toil" — it directly solves the stated problem (no more manual intervention, no host patching) without introducing Kubernetes' learning curve and platform-team requirement. Defend against "why not Kubernetes" by asking what specific capability Kubernetes would add that Fargate doesn't: if the honest answer is "resume-driven interest" or a portability requirement leadership hasn't actually stated, that's a strong signal Fargate solves the real problem with far less new operational surface.

## S3, SQS/SNS/EventBridge & Step Functions

**Beginner:** "What's the difference between SQS and SNS?"
*Ideal answer:* SQS is a queue — one message, delivered to one consumer among a competing pool, then deleted (point-to-point). SNS is a topic — one published message, delivered as an independent copy to every subscriber (pub/sub fan-out).

**Intermediate:** "Design the messaging for 'when an order is placed, both a fulfillment process and a customer-notification process need to react, independently.' Why not just have the API call both services directly?"
*Ideal answer:* SNS topic (`OrderPlaced`) fanning out to two SQS queues, one per consumer type (README.md §6). Calling both services directly from the API couples the order-placement code to knowing about every current and future consumer, and any one consumer being slow/down directly blocks or fails the order-placement request. The SNS→SQS fan-out decouples "an order happened" from "everyone who cares reacts," each independently, each with its own retry/DLQ semantics, and each scalable on its own.
*Follow-up:* "Why put an SQS queue between SNS and each consumer instead of subscribing the consumer (or its Lambda) directly to the topic?" → Direct Lambda/HTTP subscriptions have much weaker delivery/retry guarantees than a durable queue — if the subscriber is down or throttled, SNS's own retry policy is far less durable than a queue holding the message for days with its own DLQ. Never skip the queue for anything that must not silently lose a message.

**Senior:** "Walk through exactly what happens, end-to-end, when the fulfillment consumer fails to process an `OrderPlaced` message five times in a row — and what could go wrong if the DLQ has no CloudWatch alarm on it."
*Ideal answer:* Trace the full path from [diagrams/event-driven-fulfillment-sequence.md](diagrams/event-driven-fulfillment-sequence.md): the visibility timeout expires after each failed attempt, the message becomes visible again, is redelivered, and after `maxReceiveCount` (5, per [terraform/sqs.tf](terraform/sqs.tf)) is reached, SQS automatically moves it to the DLQ — no consumer code required for that move. Without an alarm on the DLQ's message count, that order is now silently stuck: not fulfilled, not visibly failed anywhere a human would notice, potentially for days, directly translating into a real customer waiting on an order that will never ship until someone happens to look. The fix is a CloudWatch alarm on `ApproximateNumberOfMessagesVisible > 0` on the DLQ specifically, wired to paging — "any DLQ message at all" is itself the signal, not a threshold.
*Follow-up:* "Why `maxReceiveCount = 5` and not 1 or 50?" → Too low (1) fails fast on transient issues that would have succeeded on retry (a momentary network blip); too high (50) delays quarantining a genuinely broken message far too long while it keeps consuming redelivery cycles. 5 (with backoff, if configured at the consumer/Step-Functions level) balances tolerating transient failures against not masking a real problem for too long — the right number is workload-specific and should be tuned from observed failure patterns, not guessed once and left forever.

**Scenario:** "Design the fulfillment saga (reserve inventory → charge payment → ship → notify) as a Step Functions state machine, including what happens when payment fails after inventory was already reserved."
*Ideal answer:* Reference the state machine in README.md §7 directly: each forward step is a Task state; a `Catch` on "Charge Payment" branches to a "Compensate: Release Inventory" state rather than leaving the reservation stranded. Explicitly name this as the distributed-systems-scale version of `OrderService.placeOrder()`'s manual `ArrayDeque`-based rollback from Module 1 — same underlying problem (can't get one atomic commit across independently-failing steps), same principle (explicitly model and execute the undo path), different scale and tooling. Call out that Step Functions doesn't give you compensation "for free" the way a database gives you `ROLLBACK` — every state with a real-world side effect needs its compensating branch designed deliberately.
*Follow-up:* "This is basically the Saga pattern — why is it in the AWS module instead of system-design/?" → This module deliberately scopes to *how Step Functions mechanically models a saga* (states, Catch branches, retry policies) — the general Saga pattern theory (choreography vs. orchestration, when to use it, comparison to 2PC) is covered in `system-design/` to avoid duplicating that treatment here.

## CloudWatch, CloudTrail & Secrets Manager

**Beginner:** "What's the difference between CloudWatch and CloudTrail?"
*Ideal answer:* CloudWatch answers "is my application healthy right now" (metrics, logs, alarms on application/infrastructure behavior). CloudTrail answers "who did what to my AWS account" (an audit log of every API call, by whom, from where) — a fundamentally different question, security/compliance-flavored rather than operational.

**Intermediate:** "Why would an application retrieve its database password from Secrets Manager at startup instead of reading it from an environment variable set in the task definition?"
*Ideal answer:* A plain environment variable in the ECS task definition is visible in plaintext to anyone who can call `DescribeTaskDefinition` — a broader audience than should be able to read a DB password — and shows up unencrypted in Terraform state/CI logs. Using the ECS task definition's `secrets` block (as in [terraform/ecs.tf](terraform/ecs.tf)) has ECS itself resolve the value from Secrets Manager at launch time; the plaintext never appears in the task definition JSON at all, only the secret's ARN does.
*Follow-up:* "What does automatic rotation add on top of just 'storing it encrypted'?" → A manually-rotated credential is, in practice, a credential that almost never actually gets rotated, because coordinated manual rotation across the secret store and every consumer is error-prone and easy to defer indefinitely. Automatic rotation (a scheduled Lambda that updates the credential in both the target system and the secret store, using a staged versioning scheme to avoid an outage during the cutover window) closes that gap without human coordination.

**Senior:** "A production incident: the app started throwing DB authentication errors at 2 AM with no application deploy around that time. Where do you look first, and why?"
*Ideal answer:* Suspect a secret rotation event — check Secrets Manager's rotation history for the DB credential around that timestamp, and check whether the rotation Lambda's staged-versioning handoff (`AWSPENDING` → `AWSCURRENT`) completed correctly or left some connections holding a stale credential. Cross-reference with CloudTrail for any `RotateSecret` or manual `PutSecretValue` calls at that time, and with CloudWatch for exactly when the app's connection pool started failing versus when any rotation event fired. This demonstrates using CloudWatch (app symptom) and CloudTrail/Secrets Manager history (root cause candidate) together, per README.md §8's "you typically need both" framing.

**Scenario:** "A compliance auditor asks: 'prove that only these three engineers could have modified the production IAM policy that grants database access, and show me every time it was actually changed in the last year.' What do you show them?"
*Ideal answer:* CloudTrail's management-event history, filtered for `PutRolePolicy`/`AttachRolePolicy`/similar IAM write actions against the specific role's ARN, over the requested window — showing the calling identity, source IP, and timestamp for every change. Combine with the account's IAM policies/SCPs showing which identities even have permission to call those IAM-modifying actions in the first place (the "could have" half of the question, not just "did"). This is precisely the class of question CloudTrail exists to answer and CloudWatch cannot — a good answer explicitly distinguishes the two rather than reaching for "we have logs" generically.

## RDS vs. DynamoDB

**Beginner:** "Why is this system's core Order/Inventory data in RDS Postgres and not DynamoDB?"
*Ideal answer:* The domain is inherently relational — an `OrderLine` must reference a real `Product` (foreign key integrity), `Order.totalAmount()` is a join-and-sum over lines, and `placeOrder()`'s all-or-nothing inventory reservation needs multi-row atomicity. RDS gives you referential integrity and ACID transactions natively; DynamoDB would require re-implementing both by hand in application code.

**Intermediate:** "Give a concrete piece of this system where you'd introduce DynamoDB alongside RDS, not instead of it, and justify the access pattern."
*Ideal answer:* An order-event audit log — append-only, extremely high write-to-read ratio, always accessed by a simple key (`orderId` + timestamp), never joined against other tables. That's DynamoDB's ideal shape: high write throughput, single-digit-ms latency, no relational structure to preserve. Justify explicitly that this is *alongside* RDS, not a replacement — the audit log referencing order IDs that live in RDS is fine; it doesn't need FK enforcement against them.
*Follow-up:* "Provisioned or On-Demand capacity for that table, and why?" → On-Demand for a workload whose volume is unpredictable or bursty (e.g. spikes during a flash sale, per EXERCISES.md #6) — pay per request, no capacity planning; Provisioned with auto-scaling once the traffic pattern is well-understood and relatively steady, since it's typically more cost-efficient at predictable volume.

**Senior:** "A teammate proposes moving the entire Order/Inventory schema to DynamoDB 'because it scales better than RDS.' How do you respond?"
*Ideal answer:* Push back with specifics, not a blanket "no": ask what scaling problem is actually being solved — DynamoDB's single-digit-ms latency at high request volume is real, but this system's core data has genuine relational integrity requirements (FK constraints, multi-row transactional atomicity) that DynamoDB doesn't provide natively; moving it would relocate that correctness burden into application code with none of the database-enforced guarantees. If the actual pain point is a specific hot access pattern (e.g. the read-heavy reporting workload README.md §10 names as a common mistake), the fix might be a read replica, not a wholesale data-model migration. "DynamoDB scales better" is true for its target access patterns and not, by itself, sufficient justification for uprooting a relational domain model.

**Scenario:** "Design a session-store migration: the security/ module's JWT layer needs to move from fully stateless tokens to server-side refresh-token tracking at scale. Would you use RDS or DynamoDB, and how would you design the table/schema?"
*Ideal answer:* DynamoDB — session data is naturally key-value (session/refresh-token ID → session blob: user ID, issued-at, expiry, device metadata), needs consistent single-digit-ms reads at potentially very high volume (every authenticated request, or at least every token refresh), and has no relational structure worth preserving. Design the partition key as the token ID itself (or a hash of it, never the raw token in plaintext), use a **TTL attribute** so DynamoDB automatically expires stale sessions without a manual cleanup job, and note explicitly that this is a case where DynamoDB's access-pattern-first design (README.md §10's "common mistakes" — design the key structure up front) matters: the partition key choice must support every real lookup this feature needs, decided before the table is built, not discovered later.

## CloudFront, Route53 & Well-Architected Framework

**Beginner:** "Why put CloudFront in front of the S3 bucket serving the Angular build, instead of pointing users at the bucket directly?"
*Ideal answer:* Latency (edge caching close to users worldwide instead of one round trip to the bucket's region), HTTPS with a custom domain (S3 static website endpoints don't support that directly), and security (the bucket can stay fully private, readable only by CloudFront via Origin Access Control, avoiding the public-bucket risk class entirely).

**Intermediate:** "What does Route53 add beyond 'just DNS' for this system, and when does it actually matter?"
*Ideal answer:* Health-check-based failover — Route53 can poll an endpoint (e.g. the ALB's health route) and stop routing traffic to it on failure, relevant specifically in a multi-region DR setup where you want automatic failover from a primary region's ALB to a secondary region's without a manual DNS change during an incident. It matters once there's an actual second environment to fail over to; configuring it with nothing on the other end is complexity without benefit.

**Senior:** "Apply all six Well-Architected pillars to one architectural decision already in this module — pick one and go deep, don't just list pillar names."
*Ideal answer:* Use README.md §12's structure but go deeper on one: e.g. the ECS-Fargate-over-EKS decision touches Performance Efficiency (right-sized operational complexity for actual scale) directly, but also Cost Optimization (Fargate's per-task billing vs. EKS's control-plane fee plus node costs even when underutilized), Operational Excellence (no Kubernetes expertise required to operate day-to-day), and Sustainability (AWS pools/optimizes shared Fargate infrastructure better than dedicated, likely-underutilized EC2/EKS nodes sized for peak load). A strong answer shows one decision has *multiple* pillar implications, not one pillar per decision in isolation.
*Follow-up:* "Where does this decision trade against Reliability or Security?" → Minimal direct trade against Security (Fargate's task-level isolation is at least as strong as an equivalent EC2 setup); a mild Reliability consideration is that Fargate task placement/capacity is AWS-managed rather than something you control down to the instance level — acceptable here since the system doesn't need that granularity, but worth naming as the trade rather than pretending the decision is free.

**Scenario:** "Amazon/JPMorgan-style: you're handed this system's architecture and told 'leadership wants to cut the AWS bill by 30% without a customer-visible change.' Walk through where you'd look, using this module's coverage."
*Ideal answer:* Systematically: (1) S3 lifecycle policies (§5) — confirm exports are actually tiering to IA/Glacier on schedule, not sitting in Standard indefinitely; (2) NAT Gateway data-processing charges (§2) — check whether AWS-service traffic (Secrets Manager, S3) could move to VPC endpoints to avoid the per-GB NAT charge; (3) ECS auto-scaling policy (§3/§12) — verify `min_capacity` isn't over-provisioned for actual off-peak traffic, and that scale-in isn't being suppressed by an overly conservative cooldown; (4) DynamoDB capacity mode (§10) — confirm On-Demand vs. Provisioned matches the actual traffic shape rather than defaulting to whichever was easiest to set up; (5) CloudWatch Logs retention (§8) — check for indefinite retention on verbose logs accumulating storage cost with no operational value. Each of these is a "customer invisible" lever specifically because none of them change externally-observable behavior or latency — the discipline is auditing cost against actual usage pattern, not cutting capability.
